# Mira — Personal AI Assistant

## What This Project Is

A Telegram bot that acts as a personal AI assistant with persistent memory.
The bot knows the user's life context — health data, friends, decisions, thoughts —
and can answer questions, structure the day, remind about things, and give advice
based on actual personal data, not generic responses.

**Example interactions:**
- "What should I get my friend Maxim for his birthday?" → bot knows Maxim's interests from memory
- Morning message → bot sends a brief with the day's priorities
- "Trained today, bench 120kg, ate well" → bot logs it and compares to last week
- "What decisions do I have pending?" → bot finds unresolved decisions from memory
- Sunday 9:00 → bot sends weekly review automatically without being asked

---

## Core Problem Being Solved

User struggles with:
1. Structuring days and maintaining a calendar
2. Personal data scattered across different apps (Notion, MyFitnessPal, etc.)
3. No AI that knows personal context when giving advice

---

## Tech Stack

- **Runtime:** .NET 9, C#
- **Telegram:** Telegram.Bot library
- **Local LLM:** Any OpenAI-compatible backend (LM Studio, llama.cpp, vLLM, etc.) — Hermes 3 8B model
- **Cloud LLM:** Anthropic Claude API (fallback for complex reasoning)
- **Storage:** Start with Notion API, SQLite as fallback
- **Health data:** MyFitnessPal export / manual logging via bot
- **Config:** appsettings.json + environment variables for secrets

---

## What the Bot Must Do

### Incoming message handling
- Accept text messages in Russian or English
- Accept voice messages → transcribe via Whisper (local, through Ollama or whisper.net)
- Route message to correct handler based on content

### Memory — what the bot knows and remembers
- **People:** friends, their interests, important dates, context
- **Health:** workouts, weight, calories, protein, goals (current: cut phase, ~1700 kcal, 130g protein)
- **Thoughts:** fleeting ideas, observations, things to think about later
- **Decisions:** important choices with reasoning, review dates
- **Daily notes:** what happened, what was planned, what was skipped

### Proactive behavior (cron jobs)
- Every morning at 8:00 → daily brief: priorities for the day, pending decisions, reminders
- Every Sunday at 9:00 → weekly review based on the week's data
- If no workout logged for 3 days → gentle reminder (not annoying)

### Commands
- `/brief` — request daily brief manually
- `/review` — request weekly review manually
- `/people` — list people in memory
- `/decisions` — list open decisions
- `/health` — health summary for last 7 days

## LLM Strategy

Two providers, different use cases:

**Local LLM (default, via OpenAI-compatible API — LM Studio, llama.cpp, vLLM, etc.):**
- Daily logging (health, thoughts)
- Simple message routing and classification
- Structuring and saving incoming data
- Zero cost, 100% private, data never leaves the machine

**Claude API (fallback for complex tasks):**
- Weekly review synthesis
- Gift ideas, purchase decisions (needs good reasoning)
- Anything requiring nuanced understanding

Switching between providers must be trivial — config change, no code changes.

## Privacy Requirements

- All personal data stays local by default
- Claude API is used only when user explicitly requests complex analysis
- Telegram bot responds only to the owner's chat ID (AllowedChatId in config)
- No logging of personal message content to external services
- Local SQLite as storage fallback if Notion API is unavailable

## Data Model

Think through and design the right entities. Suggested starting point:

**Person** — someone the user knows
- Name, relationship type
- Interests, hobbies
- Important dates (birthday etc.)
- Notes and context
- Last updated

**HealthEntry** — single health data point
- Date
- Type: workout / nutrition / weight / sleep
- Raw content (what user sent)
- Parsed data (structured: exercises, weights, calories, protein)

**Thought** — fleeting idea or observation
- Content
- Tags (auto-generated by LLM)
- Created at
- Status: active / archived

**Decision** — important choice
- Title
- Context and options considered
- Final choice and reasoning
- Review date
- Status: open / decided / reviewed

**DailyNote** — daily log
- Date
- Morning plan
- Evening summary
- Mood (optional)

## Architecture Requirements

Design the architecture yourself based on the project needs. Key constraints:

1. **LLM providers must be swappable** — Ollama and Claude must be interchangeable without touching business logic
2. **Storage must be swappable** — start with Notion, easy to swap to SQLite or anything else
3. **Business logic must not depend on external services** — testable in isolation
4. **Configuration-driven** — provider choice, API keys, chat ID all in config, never hardcoded
5. **Single responsibility** — each class does one thing

Refer to installed `dotnet-skills` plugin, specifically:
- `dotnet-project-structure` — solution layout guidance
- `dependency-injection-patterns` — DI setup
- `modern-csharp-coding-standards` — C# style
- `microsoft-extensions-configuration` — config patterns

## Development Phases

### Phase 1 — Working skeleton (start here)
Goal: bot receives a message, sends it to Ollama, returns response. Nothing is saved yet.

- Solution structure
- Telegram bot polling loop
- Single LLM provider (Ollama)
- One use case: ProcessMessage
- Hardcode a simple system prompt for now
- Bot only responds to AllowedChatId

**Done when:** you can send "hello" to the bot and get an intelligent response.

### Phase 2 — Memory
Goal: bot remembers what you tell it.

- Storage layer (Notion API or SQLite)
- Save incoming messages to appropriate category
- Retrieve relevant context before LLM call
- System prompt includes personal context

**Done when:** you tell the bot "my friend Maxim likes mechanical keyboards" and later ask
"what does Maxim like?" and get the right answer.

### Phase 3 — Structured logging
Goal: bot understands health and thought data specifically.

- Parse health messages (workout, nutrition)
- Save to HealthEntry
- Basic health summary command `/health`
- Person management

**Done when:** "bench pressed 120kg today, ate ~1800 kcal 140g protein" gets correctly
parsed and saved.

### Phase 4 — Proactive agent
Goal: bot initiates contact without being asked.

- Cron job infrastructure
- Daily brief at 8:00
- Weekly review on Sunday
- Workout reminder if 3 days no log

**Done when:** bot sends morning message automatically.

### Phase 5 — Voice messages
Goal: speak to the bot instead of typing.

- Whisper integration for transcription
- Handle Telegram voice message format
- Everything else stays the same

## Git Workflow

### Branch naming
- `main` — stable code only, no direct pushes
- `develop` — main development branch
- `feat/description` — new functionality
- `fix/description` — bug fix
- `chore/description` — infrastructure, configs, dependencies
- `refactor/description` — refactoring without behavior change

Lowercase, hyphens, specific and descriptive:
- Good: `feat/telegram-polling`, `fix/ollama-timeout`, `chore/add-github-actions`
- Bad: `feature1`, `my-branch`, `test`, `WIP`

### Commit messages
Conventional Commits, always in English:

```
feat: add Ollama provider with cancellation support
fix: handle Telegram polling timeout gracefully
chore: add GitHub Actions CI pipeline
refactor: extract message routing to separate class
test: add unit tests for ProcessMessage use case
docs: update README with setup instructions
```

Rules:
- Present tense: "add" not "added", "fix" not "fixed"
- No period at the end
- No vague messages: never "fix stuff", "WIP", "update", "changes"
- One logical change per commit

### Pull Requests
Every PR must have:
- Title in Conventional Commits format
- Description: what was done and why
- Reference to issue if exists

One PR = one task. Never mix refactoring with new functionality.

### CI/CD — GitHub Actions
Pipeline runs on every PR and push to develop:

```yaml
name: CI

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main, develop]

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-dotnet@v4
        with:
          dotnet-version: '9.0.x'
      - run: dotnet restore
      - run: dotnet build --no-restore --configuration Release
      - run: dotnet test --no-build --configuration Release
      - run: dotnet format --verify-no-changes
```

PR is not merged if CI is red. No exceptions.

## Code Review Checklist

When asking for review, I will provide the branch name, commits, and diff.
Check the following:

**Git hygiene:**
- Branch name follows naming convention
- All commits follow Conventional Commits format
- No merge commits in feature branch (rebase instead)
- No commented-out code committed

**Architecture:**
- New code fits the architecture defined in this file
- No business logic in Infrastructure layer
- No external dependencies in Core layer
- Interfaces used correctly — new providers implement existing interfaces

**C# quality:**
- CancellationToken passed and respected in all async methods
- No fire-and-forget Tasks without proper handling
- No hardcoded strings that belong in config
- Nullable reference types handled correctly

**For each issue found:** state what is wrong, where exactly, and how to fix it.
